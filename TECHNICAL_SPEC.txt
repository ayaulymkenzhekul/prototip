# Техническое задание

## 1. Общие сведения

### 1.1 Название проекта

**Смета РК / Цифровой ассистент**

### 1.2 Тип системы

Веб-приложение для создания, проверки, согласования и осмечивания дефектных ведомостей.

Система предназначена для пользователей, которые участвуют в полном жизненном цикле дефектной ведомости: от первичного описания проблемы до формирования сметы, согласования, распределения на сметчика и закрытия работ.

### 1.3 Цель проекта

Цель проекта — автоматизировать процесс создания дефектной ведомости, подбора работ и материалов, проверки документа, передачи документа в ЕСЭД/СМАКС и дальнейшего назначения сметчика.

Система должна сократить количество ручных ошибок, ускорить подготовку документа, сделать маршрут согласования прозрачным и дать пользователю понятный интерфейс, в котором видно:

- что уже заполнено;
- какие данные требуют проверки;
- какие ошибки блокируют отправку;
- какие материалы или работы подобраны автоматически;
- какие записи являются дублями;
- на каком этапе находится документ.

### 1.4 Проблема

Текущий процесс создания дефектных ведомостей часто выполняется вручную. Из-за этого возникают повторяющиеся проблемы:

- пользователь описывает дефект свободным текстом, но не всегда понимает, какие работы нужно добавить;
- работы и материалы выбираются вручную, что приводит к ошибкам в названиях, единицах измерения и объемах;
- в справочниках появляются дубли материалов и работ;
- непонятно, какие поля документа обязательны;
- пользователь не видит готовность документа к отправке;
- согласующие получают неполные или некачественно заполненные документы;
- координатор СМАКС тратит время на ручную проверку и распределение;
- сметчик получает неструктурированные данные и вынужден уточнять информацию.

### 1.5 Решение

Система должна предоставить единое рабочее пространство, где пользователь может:

- создать дефектную ведомость вручную или через Цифрового ассистента;
- описать проблему обычным языком;
- получить черновик документа;
- увидеть предлагаемые работы и материалы;
- проверить документ перед отправкой;
- исправить ошибки через подсказки Цифрового ассистента;
- отправить ДВ на согласование;
- согласовать или вернуть документ в ЕСЭД;
- передать утвержденный документ в СМАКС;
- назначить сметчика;
- выполнить осмечивание;
- закрыть смету после проверки.

Основной маршрут:

**Заявитель → ЕСЭД → СМАКС → Сметчик → Старший сметчик → Закрыто**

### 1.6 Текущее состояние проекта

Сейчас существует frontend-прототип веб-системы. Основной интерфейс реализован как монолитный HTML/CSS/JavaScript-прототип. Прототип содержит:

- рабочее место заявителя;
- создание ДВ через ЦА;
- ручное создание ДВ;
- предпросмотр документа;
- справочники;
- очередь ЕСЭД;
- очередь СМАКС;
- рабочий кабинет сметчика;
- черновик сметы;
- справочники работ, материалов и единиц измерения;
- mock-state и localStorage для демонстрации сценариев без полноценного backend.

Прототип должен рассматриваться как UX/UI-референс и основа для дальнейшей интеграции с backend.

## 2. Цели и задачи

### 2.1 Бизнес-цели

| Цель | Описание |
| --- | --- |
| Ускорить создание ДВ | Пользователь должен быстро сформировать документ через ЦА или вручную. |
| Снизить количество ошибок | Система должна подсвечивать незаполненные поля, отсутствующие работы, дубли и спорные материалы. |
| Сделать маршрут прозрачным | На каждом этапе должно быть понятно, где находится документ и кто должен выполнить действие. |
| Упростить работу сметчика | Сметчик должен получать структурированные позиции, рекомендации ЦА и историю изменений. |

Система должна обеспечивать:

1. Создание дефектной ведомости через Цифрового ассистента.
2. Ручное создание дефектной ведомости.
3. Единый live-предпросмотр документа.
4. Проверку готовности документа.
5. Работу с дефектами, работами, материалами и приложениями.
6. Отправку ДВ на согласование.
7. Очередь согласования ЕСЭД.
8. Очередь распределения СМАКС.
9. Назначение сметчика.
10. Рабочее место сметчика.
11. Подбор и замена расценок.
12. Работа со справочниками.
13. Проверку дублей.
14. Журнал действий.
15. Работу интерфейса на mock-state при отсутствии backend.

## 3. Роли пользователей

## 3.1 Заявитель / Куратор — Иванова С.М.

### Назначение роли

Заявитель является инициатором дефектной ведомости. Он описывает проблему, создает ДВ, проверяет данные, прикладывает материалы и отправляет документ на согласование.

### Основные задачи

- создать дефектную ведомость;
- описать проблему обычным языком;
- заполнить шапку ДВ;
- добавить работы;
- добавить материалы;
- загрузить приложения;
- проверить документ;
- исправить ошибки;
- отправить ДВ на согласование.

### Способы создания ДВ

#### Способ 1. Через Цифрового ассистента

1. Пользователь открывает экран создания ДВ через ЦА.
2. Вводит описание проблемы обычным языком.
3. ЦА анализирует текст.
4. ЦА определяет объект, дефекты, возможные работы и материалы.
5. ЦА формирует черновик документа.
6. Пользователь открывает предпросмотр.
7. Пользователь исправляет найденные проблемы.
8. Пользователь отправляет документ дальше.

#### Способ 2. Вручную

1. Пользователь выбирает ручное создание.
2. Заполняет описание.
3. Заполняет данные ДВ.
4. Добавляет работы.
5. Проверяет предпросмотр документа.
6. Добавляет примечания.
7. Отправляет на согласование.

### Доступные действия

| Действие | Результат |
| --- | --- |
| Создать через ЦА | Открывается сценарий создания через Цифрового ассистента. |
| Создать вручную | Открывается пошаговый мастер создания ДВ. |
| Проверить | Запускается проверка готовности документа. |
| Решить проблему | Проблема передается в чат ЦА. |
| Сохранить | Изменения сохраняются в текущем состоянии. |
| Отправить на согласование | Документ получает статус согласования и попадает в очередь ЕСЭД. |

---

## 3.2 Утверждающий ЕСЭД — Есенов Р.А.

### Назначение роли

Утверждающий ЕСЭД проверяет дефектные ведомости, поступившие на согласование. Он должен убедиться, что шапка, работы, вложения и комментарии заполнены корректно.

### Основные задачи

- видеть очередь ДВ на согласование;
- открыть документ;
- проверить общие сведения;
- проверить работы и материалы;
- проверить вложения;
- согласовать ДВ;
- вернуть ДВ на доработку с комментарием;
- передать согласованный документ в СМАКС.

### Доступные действия

| Кнопка | Поведение |
| --- | --- |
| Согласовать | Меняет статус ДВ на согласованный, документ передается в СМАКС. |
| Вернуть на доработку | Требует комментарий, меняет статус на доработку. |
| Открыть полную ДВ | Открывает live-предпросмотр документа в read-only режиме. |

---

## 3.3 Координатор СМАКС — Ким С.А.

### Назначение роли

Координатор СМАКС получает согласованные документы после ЕСЭД и распределяет их между сметчиками.

### Основные задачи

- видеть очередь согласованных ДВ;
- зарегистрировать заявку;
- проверить основание;
- проверить приоритет;
- выбрать сметчика;
- назначить сметчика;
- отложить заявку;
- вернуть заявителю при проблемах;
- передать ДВ сметчику.

### Доступные действия

| Кнопка | Поведение |
| --- | --- |
| Назначить сметчика | Назначает выбранного сметчика и меняет статус заявки. |
| Выбрать сметчика | Открывает компактную карточку выбора сметчика. |
| Отложить | Меняет статус заявки на отложенную. |
| Вернуть заявителю | Возвращает заявку с причиной. |
| Открыть полную ДВ | Открывает документ в read-only режиме. |

---

## 3.4 Сметчик — Ахметов С.Б.

### Назначение роли

Сметчик получает назначенные ДВ и формирует смету. Он проверяет позиции, подбирает расценки, работает с материалами и закрывает смету.

### Основные задачи

- видеть входящие назначенные сметы;
- открыть черновик сметы;
- проверить позиции ДВ;
- подобрать расценки;
- заменить неверные расценки;
- добавить расценку вручную;
- проверить материалы;
- задать вопрос заявителю;
- вернуть на уточнение;
- закрыть смету.

### Доступные действия

| Кнопка | Поведение |
| --- | --- |
| Открыть черновик сметы | Открывает рабочее пространство сметчика. |
| Просмотр ДВ | Открывает документ ДВ для просмотра. |
| Подобрать расценки | Открывает окно выбора расценки. |
| Задать вопрос | Открывает/активирует коммуникацию по ДВ. |
| Вернуть на уточнение | Меняет статус и требует комментарий. |
| Закрыть смету | Доступно после обработки всех позиций. |

---

## 3.5 Старший сметчик — Нурланов М.К.

### Назначение роли

Старший сметчик контролирует итоговое качество смет и работу сметчиков.

### Основные задачи

- видеть сметы, подготовленные сметчиками;
- проверять итоговую смету;
- просматривать журнал изменений;
- видеть отличия от рекомендаций ЦА;
- принимать смету;
- возвращать смету на доработку;
- контролировать качество и статусы.

### Доступные действия

| Кнопка | Поведение |
| --- | --- |
| Принять | Подтверждает итоговую смету. |
| Вернуть | Возвращает смету сметчику с комментарием. |
| Журнал изменений | Показывает историю действий. |
| Сравнить с ЦА | Показывает отличия от рекомендаций Цифрового ассистента. |

---

## 3.6 ЦА / Цифровой ассистент

### Назначение роли

Цифровой ассистент — интеллектуальный помощник, который сопровождает пользователя на всех этапах работы с ДВ и сметой.

### Основные задачи

- помогать создавать ДВ;
- анализировать описание пользователя;
- предлагать работы;
- подбирать материалы;
- находить дубли;
- объяснять выбор позиции;
- проверять готовность документа;
- помогать исправлять ошибки через чат;
- сопровождать пользователя в предпросмотре, справочниках, ЕСЭД, СМАКС и черновике сметы.

### Обязательное поведение

ЦА не должен быть только декоративным чатом. Его действия должны менять mock-state или реальные данные:

- добавлять работу;
- подтверждать материал;
- менять статус ошибки;
- обновлять готовность документа;
- предлагать решение дубля;
- формировать объяснение выбора.

## 4. Бизнес-процесс

### 4.1 Основной маршрут

1. Заявитель создает ДВ.
2. ЦА помогает заполнить документ.
3. Заявитель проверяет предпросмотр документа.
4. Если есть ошибки, ЦА помогает их исправить.
5. ДВ отправляется на согласование.
6. ЕСЭД утверждает или возвращает ДВ на доработку.
7. После утверждения ДВ попадает в СМАКС.
8. Координатор СМАКС назначает сметчика.
9. Сметчик открывает черновик сметы.
10. Сметчик проверяет позиции и подбирает расценки.
11. Смета закрывается.
12. При необходимости старший сметчик проверяет итоговую смету.

Схема:

```text
Заявитель → ЕСЭД → СМАКС → Сметчик → Старший сметчик → Закрыто
```

### 4.2 Альтернативный маршрут: возврат на доработку

```text
ЕСЭД → Возврат на доработку → Заявитель → Исправление → Повторная отправка
```

### 4.3 Альтернативный маршрут: возврат из СМАКС

```text
СМАКС → Возврат заявителю → Заявитель → Исправление основания/данных → Повторная передача
```

### 4.4 Альтернативный маршрут: уточнение от сметчика

```text
Сметчик → Вопрос заявителю → Заявитель уточняет → Сметчик продолжает осмечивание
```

## 5. Статусы

### 5.1 Статусы ДВ и сметы

| Статус | Кто видит | Кто может изменить | Значение | Доступные действия |
| --- | --- | --- | --- | --- |
| Черновик | Заявитель | Заявитель, ЦА | Документ создается, еще не отправлен. | Редактировать, проверить, добавить работы, добавить материалы, открыть предпросмотр. |
| На согласовании | Заявитель, ЕСЭД | ЕСЭД | Документ отправлен на согласование. | Открыть ДВ, согласовать, вернуть на доработку. |
| Согласовано | Заявитель, ЕСЭД, СМАКС | ЕСЭД, СМАКС | ДВ согласована и готова к передаче в СМАКС. | Передать в СМАКС, открыть полную ДВ. |
| Внешнее согласование | Заявитель, ЕСЭД | ЕСЭД | Документ проходит внешний этап согласования. | Проверить, согласовать, вернуть. |
| На утверждении | ЕСЭД | ЕСЭД | Документ ожидает финального решения утверждающего. | Согласовать, вернуть на доработку. |
| Утверждена | ЕСЭД, СМАКС | СМАКС | Документ утвержден и ожидает регистрации/распределения. | Зарегистрировать, назначить сметчика. |
| На доработке | Заявитель, ЕСЭД | Заявитель | Документ возвращен с замечаниями. | Исправить, повторно отправить. |
| На осмечивании | Сметчик, СМАКС | Сметчик | ДВ назначена сметчику, идет подготовка сметы. | Открыть черновик, подобрать расценки, задать вопрос. |
| Смета готова | Сметчик, старший сметчик | Сметчик, старший сметчик | Сметчик завершил подготовку. | Проверить, принять, вернуть. |
| Закрыто | Все роли с доступом | Старший сметчик / система | Процесс завершен. | Только просмотр, журнал, экспорт. |

### 5.2 Внутренние статусы проверки

| Статус | Значение | Визуальный стиль |
| --- | --- | --- |
| Готов | Данные подтверждены, действие не требуется. | Зеленый badge. |
| Нужно уточнение | Есть данные, требующие подтверждения. | Желтый/оранжевый badge. |
| Нет решения | ЦА или пользователь не выбрали работу/материал. | Красный badge. |
| Ошибка | Блокирующая проблема. | Красный badge/error row. |
| Дубль | Найдена похожая запись в справочнике. | Желтый badge, карточка сравнения. |
| AI-подбор | Позиция предложена ЦА. | Синий/голубой badge. |
| Из справочника | Позиция взята из утвержденного справочника. | Нейтральный/синий badge. |
| Ручной ввод | Позиция добавлена пользователем вручную. | Серый/оранжевый badge. |

## 6. Страницы и сценарии

### 6.1 Общая структура интерфейса

Интерфейс должен состоять из следующих зон:

| Зона | Назначение |
| --- | --- |
| Левый sidebar | Основная навигация по роли пользователя. |
| Верхний app bar | Контекст страницы, действия, уведомления, выход. |
| Рабочая область | Основной контент страницы. |
| Правая панель | ЦА, detail panel, карточка выбранного объекта или задачи. |
| Модальные окна | Выбор расценок, редактирование, подтверждения. |
| Toast/inline messages | Результат действий и ошибки. |

### 6.2 Требования к layout

- Интерфейс должен быть светлым.
- Основной цвет действий — синий.
- Success — зеленый.
- Warning — желтый/оранжевый.
- Error — красный.
- Все иконки должны быть в одном стиле.
- Кнопки должны быть визуально кликабельны.
- Не должно быть больших пустых областей.
- На масштабе браузера 100% интерфейс не должен ломаться.
- Sidebar и app bar не должны дублировать друг друга.
- Правая панель ЦА должна занимать всю доступную высоту.
- Input чата должен быть закреплен снизу.
- Tabs и stepper должны быть кликабельными.

## 6.4 Страница создания ДВ через ЦА

### Название страницы

**Создание ДВ через ЦА**

### Назначение

Экран нужен для быстрого создания дефектной ведомости через свободное описание проблемы.

### Основные элементы

| Элемент | Описание |
| --- | --- |
| Большое поле описания | Пользователь вводит проблему обычным языком. |
| Демо-сценарий | Кнопка для подстановки тестового текста. |
| Создать через ЦА | Запускает анализ и формирование черновика. |
| Создать вручную | Переводит пользователя в ручной сценарий. |
| Правая панель | Объясняет, что будет дальше. |

### Правая панель "Что будет дальше"

1. ЦА определит объект и тип работ.
2. Сформирует черновик шапки.
3. Предложит работы из каталога.
4. Попросит уточнить недостающие данные.
5. Подготовит ДВ к согласованию.

### Логика

1. Пользователь вводит описание.
2. Нажимает "Создать через ЦА".
3. ЦА анализирует текст.
4. Создается черновик ДВ.
5. Открывается live-предпросмотр документа.
6. Все найденные проблемы отображаются в блоке готовности.

### Валидация

- Нельзя создать ДВ через ЦА с пустым описанием.
- Если описание слишком короткое, показать предупреждение.
- Если ЦА не может определить объект, показать проблему в readiness checklist.

## 6.5 Ручное создание ДВ

### Flow

1. Описание.
2. Данные ДВ.
3. Работы.
4. Предпросмотр документа.
5. Примечания.
6. Согласование.

### Шаг 1. Описание

**Цель:** зафиксировать первичное описание проблемы.

Поля:

- описание дефекта;
- объект/локация;
- дата;
- заявитель.

Кнопки:

- Далее;
- Назад;
- Создать через ЦА.

Проверки:

- описание не должно быть пустым;
- объект должен быть выбран или введен.

### Шаг 2. Данные ДВ

**Цель:** заполнить шапку документа.

Поля:

- номер ДВ;
- предприятие;
- объект;
- основание;
- куратор;
- заявитель;
- дата осмотра;
- подразделение.

Кнопки:

- Далее;
- Назад;
- Сохранить черновик.

Проверки:

- обязательные поля должны быть заполнены;
- дата должна быть корректной;
- номер ДВ не должен дублироваться.

### Шаг 3. Работы

**Цель:** добавить работы в документ.

Элементы:

- каталог работ;
- поиск;
- список выбранных работ;
- карточка выбранной работы;
- материалы, связанные с работой.

Кнопки:

- Добавить работу;
- Удалить работу;
- Выбрать из каталога;
- Далее.

Проверки:

- должна быть хотя бы одна работа;
- единица измерения должна быть указана;
- объем должен быть заполнен или помечен как требующий уточнения.

### Шаг 4. Предпросмотр документа

**Цель:** показать live-документ перед примечаниями и согласованием.

Требование:

После шага "Работы" обязательно должна открываться страница "Предпросмотр документа", а не сразу "Примечания".

Кнопки:

- Проверить;
- Редактировать;
- Сохранить;
- Далее;
- Назад.

### Шаг 5. Примечания

**Цель:** добавить комментарии и уточнения перед отправкой.

Поля:

- комментарий заявителя;
- служебные примечания;
- дополнительное описание.

### Шаг 6. Согласование

**Цель:** финальная отправка документа.

Кнопки:

- Отправить на согласование;
- Вернуться к предпросмотру;
- Сохранить черновик.

Проверки:

- документ не должен иметь blocking errors;
- объект должен быть заполнен;
- работы должны быть добавлены;
- дубли материалов должны быть обработаны.

## 6.6 Предпросмотр документа ДВ

### Назначение

Предпросмотр документа — это не PDF viewer, а live document workspace. Пользователь должен видеть документ, редактировать данные при наличии прав, проверять ошибки и взаимодействовать с ЦА.

### Layout

| Зона | Описание |
| --- | --- |
| Левая панель | Ведомости, справочники, дефекты, объекты. |
| Центральная область | Live-документ ДВ. |
| Правая панель | Чат ЦА и next best action. |

### Левая панель

Вкладки:

- Ведомости;
- Справочники.

В режиме "Ведомости" отображаются:

- поиск;
- дефекты текущей ведомости;
- мои ведомости;
- объекты и локации;
- кнопка "+ Создать ведомость".

В режиме "Справочники" отображаются:

- Объекты / Локации;
- Материалы;
- Работы;
- Единицы измерения;
- блок качества данных.

### Центральная область

Верхний stepper:

```text
Черновик → Согласование → Сборка дефектов → Осмечивание → Закрыто
```

Tabs документа:

- Общие;
- Дефекты;
- Приложения;
- Комментарии;
- Подписи.

Главные блоки:

1. Карточка готовности.
2. Документ "Дефектная ведомость".
3. Секции документа.

### Блок готовности

Показывает:

- progress, например 70%;
- checklist;
- ошибки;
- предупреждения;
- блокирующие пункты;
- кнопки "Решить", "Открыть", "Проверить заново".

Пример checklist:

| Пункт | Статус |
| --- | --- |
| Объект, основание и даты заполнены | Готов |
| Приложены подтверждающие материалы | Готов |
| Объемы проставлены по всем работам | Готов |
| У дефекта нет работ | Ошибка |
| Работы требуют уточнения | Предупреждение |
| Возможный дубль материала | Дубль |

#### 1. Общие сведения

Поля:

- объект / локация;
- заявитель;
- основание;
- дата осмотра;
- заказчик;
- планируемая дата работ;
- подразделение;
- куратор;
- участок;
- статус.

#### 2. Дефекты / Работы / Материалы

Для каждого дефекта:

- номер;
- название;
- статус;
- confidence;
- фото;
- что увидел ЦА;
- список работ;
- список материалов;
- trust layer;
- действия.

#### 3. Приложения

Отображает:

- фото;
- PDF;
- акты;
- планы помещения;
- другие файлы.

#### 4. Комментарии

Отображает:

- комментарии заявителя;
- комментарии ЦА;
- комментарии согласующих;
- комментарии сметчика.

#### 5. Подписи и согласование

Поля:

- заявитель;
- куратор;
- сметчик;
- дата.

### Правая панель ЦА

Состав:

- заголовок "Цифровой ассистент";
- сообщения;
- контекст текущей проблемы;
- next best action;

### Особая логика

| Действие | Поведение |
| --- | --- |

## 7. Логика ЦА

### 7.1 Общие требования

ЦА должен работать во всех ключевых сценариях:

- создание ДВ;
- предпросмотр;
- справочники;
- проверка готовности;
- обработка дублей;
- подбор работ и материалов;
- черновик сметы;
- объяснение решений.

ЦА должен менять состояние интерфейса. Если backend отсутствует, изменения должны происходить через mock-state/localStorage.

### 7.2 Сценарий: у дефекта нет работ

1. В checklist появляется ошибка.
2. Пользователь нажимает "Решить".
3. Контекст ошибки передается в чат.
4. ЦА предлагает одну или несколько работ.
5. Пользователь выбирает работу.
6. Работа добавляется к дефекту.
7. Статус ошибки меняется.
8. Readiness пересчитывается.

### 7.3 Сценарий: работа требует уточнения

1. Система помечает работу статусом "Нужно уточнение".
2. ЦА задает уточняющий вопрос.
3. Пользователь выбирает вариант или вводит ответ.
4. Confidence повышается.
5. Статус меняется на готовый или остается предупреждением.

### 7.4 Сценарий: дубль материала

1. ЦА находит похожие записи.
2. Показываются две или более записи.
3. Пользователь выбирает действие:
   - использовать существующий;
   - объединить;
   - оставить отдельно.
4. Статус дубля обновляется.
5. Readiness пересчитывается.

### 7.5 Сценарий: принять подбор

1. Пользователь нажимает "Принять подбор".
2. Материалы или работы считаются подтвержденными.
3. Trust layer обновляется.
4. Готовность документа растет.

### 7.6 Сценарий: проверить заново

1. Пользователь нажимает "Проверить заново".
2. ЦА повторно анализирует документ.
3. Checklist обновляется.
4. Progress пересчитывается.
5. Система показывает toast.

## 9. UI/UX требования

### 9.1 Общий стиль

Интерфейс должен выглядеть как современная enterprise SaaS-система:

- светлая тема;
- белые карточки;
- спокойный фон;
- аккуратные границы;
- мягкие тени;
- скругления 14-20px;
- читаемые таблицы;
- плотная, но не перегруженная компоновка.

### 9.2 Цвета

| Назначение | Цвет |
| --- | --- |
| Primary | Синий |
| Success | Зеленый |
| Warning | Желтый/оранжевый |
| Error | Красный |
| Neutral | Серый |

### 9.3 Компоненты

Требования:

- карточки не должны быть вложены друг в друга без необходимости;
- таблицы должны быть читаемыми;
- tabs должны иметь активное состояние;
- stepper должен показывать текущий этап;
- кнопки должны иметь hover/active состояния;
- все иконки должны быть в одном стиле;
- текст не должен вылезать за границы;
- длинные строки должны переноситься или сокращаться корректно.

### 9.4 Адаптация

Минимальные требования:

- интерфейс не должен ломаться при 100% масштабе браузера;
- основные страницы должны быть usable на ноутбуке;
- боковые панели не должны перекрывать основной документ;
- чат должен сохранять input внизу.

## 10. Интерактивность

### 10.1 Общие требования

Все кнопки должны иметь обработчики.

Если backend отсутствует:

- использовать mock-state;
- изменять данные в памяти;
- изменять localStorage;
- показывать toast;
- визуально обновлять страницу.

Нельзя оставлять декоративные кнопки без результата.

### 10.2 Требования к действиям

Для каждого действия должно быть определено:

- что происходит;
- какой статус меняется;
- какой toast показывается;
- куда переходит пользователь;
- какие счетчики обновляются.

### 10.3 Примеры интерактивности

| Действие | Результат |
| --- | --- |
| Согласовать в ЕСЭД | Статус меняется, запись уходит в СМАКС, появляется toast. |
| Вернуть на доработку | Требуется комментарий, статус меняется, появляется уведомление. |
| Назначить сметчика | Заявка получает сметчика и статус назначения. |
| Принять подбор ЦА | Позиция становится подтвержденной. |
| Объединить дубли | Дубль помечается как обработанный. |
| Проверить заново | Readiness пересчитывается. |

## 11. Валидация

### 11.1 Проверки ДВ

Система не должна разрешать отправку ДВ, если:

- не заполнен объект;
- нет работ;
- есть blocking errors;
- нет обязательных дат;
- отсутствует заявитель;
- не обработаны критичные дубли материалов;
- есть позиция без единицы измерения;
- есть позиция без объема, если объем обязателен.

### 11.2 Проверки ЕСЭД

- Возврат на доработку требует комментарий.
- Согласование невозможно, если документ не открыт или не выбран.
- После согласования статус должен измениться.

### 11.3 Проверки СМАКС

- Назначение требует выбранного сметчика.
- Нельзя назначить заявку, которая уже закрыта.
- Возврат заявителю требует причину.

### 11.4 Проверки сметчика

- Закрытие сметы требует, чтобы все позиции были обработаны.
- Нельзя закрыть смету с незамененной ошибочной расценкой.
- Нельзя принять позицию без расценки.

### 11.5 Ошибки интерфейса

Ошибки должны отображаться через:

- toast;
- inline message;
- подсветку поля;
- warning card.

## 12. Acceptance Criteria

### 12.1 Функциональные критерии

1. Все роли открывают свои страницы.
2. Навигация работает для каждой роли.
3. Создание ДВ через ЦА работает.
4. Ручное создание ДВ работает.
5. После шага "Работы" открывается предпросмотр документа.
6. Предпросмотр документа показывает live document workspace.
7. Поля документа редактируются в edit mode.
8. Поля документа не редактируются в read-only mode.
9. ЦА помогает решать ошибки.
10. Дубли материалов можно обработать.
11. Readiness пересчитывается после действий.
12. ЕСЭД может согласовать ДВ.
13. ЕСЭД может вернуть ДВ на доработку.
14. СМАКС может назначить сметчика.
15. СМАКС может отложить заявку.
16. СМАКС может вернуть заявку заявителю.
17. Сметчик может открыть черновик.
18. Сметчик может подобрать расценку.
19. Сметчик может заменить расценку.
20. Сметчик может закрыть смету после проверки всех позиций.
21. Старший сметчик может просмотреть итоговую смету.
22. Все кнопки имеют обработчики.
23. Все важные действия показывают toast или inline result.
24. Нет пустых страниц.
25. Нет console errors.

### 12.2 UI/UX критерии

1. Интерфейс не ломается на 100% масштабе браузера.
2. Нет больших пустых областей.
3. Sidebar отображает корректные пункты для роли.
4. App bar не дублирует sidebar.
5. Правая панель ЦА full-height.
6. Input чата закреплен снизу.
7. Tabs кликабельны.
8. Stepper кликабелен.
9. Таблицы читаемые.
10. Badge статусов визуально различимы.
11. Кнопки имеют понятное активное/disabled состояние.

### 12.3 Критерии интеграции с backend

1. API описан через Swagger/OpenAPI.
2. Секреты не хранятся во frontend-коде.
3. Авторизация работает через backend.
4. Данные ДВ сохраняются на сервере.
5. Справочники приходят с backend.
6. Очереди ЕСЭД и СМАКС приходят с backend.
7. Действия пользователей фиксируются в истории.
8. Frontend корректно обрабатывает ошибки API.

## 13. Технические требования

### 13.1 Frontend

Frontend может быть реализован:

- на текущей основе HTML/CSS/JavaScript для прототипа;
- либо перенесен на современный frontend-фреймворк по решению команды.

Обязательные требования:

- повторить текущую логику прототипа;
- сохранить ключевые сценарии;
- обеспечить кликабельность кнопок;
- подключить API;
- убрать зависимость production-логики от localStorage.

### 13.2 Backend

Рекомендуемый стек:

- C#;
- .NET;
- ASP.NET Core;
- REST API;
- Swagger/OpenAPI.

### 13.3 API

Нужны методы:

- авторизация;
- получение списка ДВ;
- создание ДВ;
- обновление ДВ;
- получение ДВ по id;
- отправка ДВ на согласование;
- согласование ДВ;
- возврат ДВ на доработку;
- получение очереди ЕСЭД;
- получение очереди СМАКС;
- назначение сметчика;
- получение справочников;
- создание записи справочника;
- обновление записи справочника;
- архивирование записи;
- проверка дублей;
- загрузка файлов;
- запрос к Цифровому ассистенту.

### 13.4 Безопасность

- Пароли, токены, cookie и ключи не должны храниться во frontend.
- Все секреты должны храниться на backend или в переменных окружения.
- Доступ к страницам должен зависеть от роли.
- Все действия должны проверяться на backend.

Для разработки backend/frontend интеграции необходимо предоставить:

4. Описание ролей и прав.

## 15. Итог

Проект "Смета РК / Цифровой ассистент" должен стать веб-системой, которая объединяет создание ДВ, проверку качества, работу ЦА, согласование ЕСЭД, распределение СМАКС, работу сметчика и управление справочниками.

Ключевое требование: интерфейс должен быть не набором статичных экранов, а рабочим прототипом с понятной логикой переходов, обновлением статусов, обработкой ошибок и видимым результатом каждого действия.
