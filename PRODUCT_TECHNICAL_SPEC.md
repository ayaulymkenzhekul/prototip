# Техническое задание

## Термины и сокращения

| Термин | Расшифровка / значение |
| --- | --- |
| ДВ | Дефектная ведомость. Документ, в котором фиксируются выявленные дефекты, объект, работы, материалы, приложения, комментарии и маршрут согласования. |
| ЦА | Цифровой ассистент. Помощник системы, который анализирует данные, предлагает работы и материалы, помогает исправлять ошибки и подбирать расценки. |
| ЕСЭД | Этап согласования документа утверждающим лицом. В рамках проекта используется как очередь и рабочее место утверждающего. |
| СМАКС | Этап регистрации, проверки и распределения согласованной ДВ на сметчика. |
| Осмечивание | Процесс подбора расценок, проверки позиций ДВ и формирования сметы. |
| Сметчик | Специалист, который обрабатывает ДВ, подбирает расценки и готовит смету. |
| Старший сметчик | Пользователь, который контролирует качество готовых смет и принимает итоговое решение. |
| Blocking error | Блокирующая ошибка, из-за которой документ нельзя отправить дальше по маршруту. |
| Readiness / готовность | Показатель готовности ДВ к следующему этапу процесса. |
| Справочник | Набор утвержденных записей: объекты, локации, материалы, работы, единицы измерения. |

## 1. Общие сведения

### 1.1 Название проекта

**Смета РК / Цифровой ассистент**

### 1.2 Назначение системы

Система "Смета РК / Цифровой ассистент" предназначена для организации полного цикла работы с дефектными ведомостями: от первичного описания дефекта заявителем до согласования документа, передачи в СМАКС, назначения сметчика, подбора расценок, проверки сметы и закрытия процесса.

Система должна использоваться участниками процесса как единое рабочее пространство, где каждый пользователь видит только свои задачи, понятный статус документа, доступные действия и подсказки Цифрового ассистента.

### 1.3 Тип системы

Веб-система для создания, проверки, согласования, распределения и осмечивания дефектных ведомостей.

### 1.4 Цель проекта

Главная цель проекта - автоматизировать процесс работы с дефектными ведомостями:

- заявитель описывает дефект и формирует ДВ;
- Цифровой ассистент помогает подобрать работы и материалы;
- документ проходит проверку готовности;
- ДВ передается на согласование в ЕСЭД;
- после согласования документ попадает в СМАКС;
- координатор назначает сметчика;
- сметчик подбирает расценки и закрывает смету;
- старший сметчик при необходимости проверяет итог.

### 1.5 Проблема, которую решает система

В текущем процессе работа с дефектными ведомостями часто выполняется вручную и зависит от внимательности участников. Из-за этого возникают типовые проблемы:

- дефект описан обычным текстом, но не переведен в корректные работы;
- в документе отсутствуют обязательные поля;
- работы и материалы указаны неточно;
- объемы требуют уточнения;
- в справочниках появляются дубли;
- согласующие получают неполные документы;
- координатор СМАКС вручную распределяет заявки;
- сметчик тратит время на уточнение исходных данных;
- участники процесса не всегда понимают, на каком этапе находится документ.

### 1.6 Краткое описание решения

Система должна объединить в одном продукте:

- создание ДВ через Цифрового ассистента;
- ручное создание ДВ;
- live-предпросмотр документа;
- проверку готовности документа;
- работу с ошибками, предупреждениями и дублями;
- маршрут согласования;
- очередь ЕСЭД;
- очередь СМАКС;
- назначение сметчика;
- рабочее место сметчика;
- черновик сметы;
- проверку старшим сметчиком;
- управление справочниками.

Основной маршрут процесса:

```text
Заявитель -> ЕСЭД -> СМАКС -> Сметчик -> Старший сметчик -> Закрыто
```

## 3. Общий бизнес-процесс

### 3.1 Основной маршрут

1. Заявитель создает дефектную ведомость.
2. Цифровой ассистент помогает заполнить документ.
3. Заявитель проверяет предпросмотр ДВ.
4. Если есть ошибки, заявитель исправляет их вручную или через Цифрового ассистента.
5. ДВ отправляется в ЕСЭД.
6. Утверждающий ЕСЭД согласует ДВ или возвращает ее на доработку.
7. После согласования ДВ попадает в СМАКС.
8. Координатор СМАКС проверяет заявку и назначает сметчика.
9. Сметчик открывает входящую смету.
10. Сметчик проверяет позиции ДВ и подбирает расценки.
11. Сметчик закрывает смету.
12. Старший сметчик при необходимости проверяет итог.
13. Процесс завершается статусом "Закрыто".

### 3.2 Возврат на доработку из ЕСЭД

Если утверждающий ЕСЭД обнаруживает проблему, он возвращает ДВ заявителю. Возврат должен сопровождаться обязательным комментарием. После исправления заявитель повторно отправляет ДВ на согласование.

```text
ЕСЭД -> На доработке -> Заявитель -> Повторная отправка -> ЕСЭД
```

### 3.3 Возврат из СМАКС

Если координатор СМАКС видит, что ДВ нельзя передать сметчику, он возвращает документ заявителю с причиной. Например, отсутствует основание, неясен приоритет, есть конфликт в объекте или требуется уточнение.

```text
СМАКС -> Возврат заявителю -> Заявитель -> Исправление -> Повторная передача
```

### 3.4 Уточнение от сметчика

Если сметчик не может подобрать расценку или сомневается в объеме/работе, он задает вопрос заявителю. До получения ответа позиция может иметь статус "Нужно уточнение".

```text
Сметчик -> Вопрос заявителю -> Ответ заявителя -> Продолжение осмечивания
```

| На утверждении | Документ ожидает финального утверждения. | ЕСЭД | Утверждающий ЕСЭД | Утверждена, На доработке |
| На доработке | Документ возвращен заявителю с замечаниями. | Заявитель, ЕСЭД, СМАКС | Заявитель | Черновик, На согласовании |
| На осмечивании | ДВ назначена сметчику, идет подбор расценок. | СМАКС, сметчик, заявитель | Сметчик | Смета готова, На доработке |
| Смета готова | Сметчик завершил обработку позиций. | Сметчик, старший сметчик, СМАКС | Старший сметчик | Закрыто, На осмечивании |
| Закрыто | Процесс завершен, документ доступен только для просмотра и истории. | Все роли с доступом | Система / старший сметчик | - |

### 5.2 Внутренние статусы проверки

| Статус | Значение | Где используется |
| --- | --- | --- |
| Готов | Данные заполнены и подтверждены. | Checklist, позиции ДВ, материалы, расценки. |
| Нужно уточнение | Данные есть, но требуют ответа пользователя или проверки. | Работы, материалы, объемы, расценки. |
| Нет решения | Для проблемы не выбран вариант решения. | Ошибки готовности, дефекты без работ. |
| Ошибка | Блокирующая проблема, которая мешает отправке или закрытию. | Проверка ДВ, закрытие сметы, обязательные поля. |
| Дубль | Найдена похожая запись или повтор материала/работы. | Справочники, материалы, карточка проверки. |
| AI-подбор | Позиция предложена Цифровым сметчиком. | Работы, материалы, расценки. |
| Из справочника | Позиция выбрана из утвержденного справочника. | Работы, материалы, единицы измерения. |
| Ручной ввод | Позиция добавлена пользователем вручную. | Работы, материалы, комментарии. |

## 6. Функциональные требования

### 6.1 Создание ДВ через ЦА

Система должна предоставлять сценарий создания ДВ через Цифрового ассистента.

Пользователь должен иметь возможность:

- ввести описание дефекта обычным языком;
- указать объект или оставить его для определения ЦА;
- запустить анализ описания;
- получить черновик ДВ;
- увидеть предложенные дефекты, работы и материалы;
- увидеть список вопросов и уточнений;
- перейти в предпросмотр документа.

Цифровой ассистент должен:

- определить тип дефекта;
- предложить объект/локацию, если это возможно;
- предложить работы;
- предложить материалы;
- отметить неуверенные места;
- сформировать список ошибок и предупреждений.

После создания черновика система должна открыть предпросмотр ДВ, где пользователь может проверить и исправить данные.

### 6.2 Ручное создание ДВ

Ручное создание ДВ должно быть организовано как пошаговый сценарий:

1. Описание.
2. Данные ДВ.
3. Работы.
4. Предпросмотр документа.
5. Примечания.
6. Согласование.

Важно: после шага "Работы" обязательно должен открываться шаг "Предпросмотр документа". Нельзя сразу переводить пользователя к примечаниям или отправке, потому что он должен увидеть итоговый вид документа и список проблем.

#### Шаг 1. Описание

Пользователь вводит:

- краткое описание дефекта;
- подробное описание;
- объект или локацию;
- дату осмотра;
- инициатора или куратора.

#### Шаг 2. Данные ДВ

Пользователь заполняет:

- номер ДВ;
- объект;
- локацию;
- основание;
- заявителя;
- куратора;
- подразделение;
- планируемую дату работ;
- статус.

#### Шаг 3. Работы

Пользователь выбирает или добавляет:

- работы;
- единицы измерения;
- объемы;
- характеристики;
- приоритет;
- связанные материалы.

#### Шаг 4. Предпросмотр документа

Система показывает live-документ ДВ, блок готовности, ошибки, предупреждения и подсказки ЦА.

#### Шаг 5. Примечания

Пользователь добавляет:

- комментарии;
- служебные примечания;
- пояснения для согласующего или сметчика.

#### Шаг 6. Согласование

Перед отправкой система проверяет:

- заполнен ли объект;
- есть ли работы;
- нет ли блокирующих ошибок;
- обработаны ли критичные дубли;
- заполнены ли обязательные поля.

### 6.3 Предпросмотр документа ДВ

Предпросмотр документа должен быть реализован как **live document workspace**, а не как статичный PDF.

#### Левая зона

Слева должна быть навигация по контексту документа:

- вкладка "Ведомости";
- вкладка "Справочники";
- поиск;
- дефекты текущей ведомости;
- мои ведомости;
- объекты и локации;
- кнопка создания новой ведомости.

#### Центральная зона

В центре должен отображаться документ ДВ:

- stepper маршрута;
- tabs документа;
- блок готовности;
- секция "Общие сведения";
- секция "Дефекты / Работы / Материалы";
- секция "Приложения";
- секция "Комментарии";
- секция "Подписи".

Stepper должен показывать этапы:

```text
Черновик -> Согласование -> Сборка дефектов -> Осмечивание -> Закрыто
```

Tabs документа:

- Общие;
- Дефекты;
- Приложения;
- Комментарии;
- Подписи.

#### Блок готовности

Блок готовности должен показывать:

- процент готовности;
- список выполненных проверок;
- ошибки;
- предупреждения;
- блокирующие проблемы;
- кнопку "Решить";
- кнопку "Открыть";
- кнопку "Проверить заново".

Пример проверок:

| Проверка | Возможный статус |
| --- | --- |
| Объект и основание заполнены | Готов |
| Приложены подтверждающие материалы | Готов |
| Объемы указаны по всем работам | Готов / Нужно уточнение |
| У дефекта есть работы | Готов / Ошибка |
| Материалы проверены на дубли | Готов / Дубль |

#### Правая зона

Справа должна быть панель Цифрового ассистента:

- заголовок;
- контекст текущего документа;
- сообщения;
- next best action;
- быстрые кнопки;
- поле ввода вопроса;
- кнопка отправки.

Панель ЦА должна помогать пользователю принимать решения, а не быть декоративным чатом.

### 6.4 ЕСЭД

Страница ЕСЭД предназначена для утверждающего.

На странице должны быть:

- заголовок очереди;
- карточки статистики;
- список ДВ на согласовании;
- фильтры;
- карточка выбранной ДВ;
- история действий;
- блок комментариев;
- кнопки действий.

Карточка ДВ должна показывать:

- номер ДВ;
- объект;
- заявителя;
- дату;
- статус;
- приоритет;
- наличие вложений;
- результат проверки.

Доступные действия:

- "Согласовать";
- "Вернуть на доработку";
- "Открыть полную ДВ".

Кнопка "Открыть полную ДВ" должна открывать документ в режиме просмотра без возможности редактирования.

### 6.5 СМАКС

Страница СМАКС предназначена для координатора распределения.

На странице должны быть:

- очередь распределения;
- список согласованных ДВ;
- статистика;
- фильтры;
- detail panel выбранной заявки;
- блок выбора сметчика;
- история действий;
- комментарии.

Выбор сметчика должен быть компактным:

- по умолчанию показывается выбранный или рекомендованный сметчик;
- по клику открывается карточка выбора;
- выбор выполняется через radio-button;
- основная кнопка меняет текст в зависимости от выбранного сметчика.

Доступные действия:

- "Назначить сметчика";
- "Отложить";
- "Вернуть заявителю";
- "Открыть полную ДВ".

После назначения ДВ должна перейти сметчику в работу.

### 6.6 Рабочее место сметчика

Рабочее место сметчика должно показывать:

- входящие сметы;
- список назначенных ДВ;
- статусы обработки;
- прогресс осмечивания;
- карточку выбранной задачи;
- комментарии;
- быстрые действия.

Сметчик должен иметь возможность:

- открыть входящую смету;
- открыть ДВ в режиме просмотра;
- открыть черновик сметы;
- подобрать расценку;
- задать вопрос заявителю;
- вернуть на уточнение;
- закрыть смету.

Система должна показывать сметчику, какие позиции уже обработаны, какие требуют внимания и какие заблокированы ошибками.

### 6.7 Черновик сметы

Черновик сметы предназначен для обработки позиций ДВ и выбора расценок.

Экран должен содержать:

- заголовок сметы;
- данные ДВ;
- список позиций;
- предложенную расценку ЦА;
- статус каждой позиции;
- комментарии;
- итоговый обзор;
- журнал действий.

Для каждой позиции должны быть доступны действия:

- "Принять";
- "Заменить";
- "Добавить вручную";
- "Отклонить";
- "Комментарий";
- "Прикрепить файл".

Окно выбора расценки должно содержать:

- поиск;
- категории;
- рекомендации ЦА;
- список расценок;
- preview выбранной расценки;
- кнопку выбора;
- возможность вернуться без сохранения.

Если пользователь выбирает несколько позиций или материалов, окно не должно закрываться после первого выбора, пока сценарий не завершен.

### 6.8 Старший сметчик

Старший сметчик должен иметь страницу проверки готовых смет.

На странице должны быть:

- очередь готовых смет;
- карточка выбранной сметы;
- итоговые показатели;
- журнал изменений;
- сравнение с рекомендациями ЦА;
- комментарии сметчика;
- решения старшего сметчика.

Доступные действия:

- принять смету;
- вернуть смету на доработку;
- открыть журнал изменений;
- посмотреть отличия от рекомендаций ЦА;
- оставить комментарий.

### 6.9 Справочники

Система должна содержать справочники:

- объекты / локации;
- материалы;
- работы;
- единицы измерения.

Для каждого справочника должны быть доступны:

- поиск;
- фильтрация;
- список записей;
- карточка записи;
- добавление записи;
- редактирование записи;
- архивирование записи;
- проверка дублей;
- показатель качества данных.

#### Справочник работ

Справочник работ должен поддерживать классификацию по уровням:

- раздел;
- подраздел;
- группа;
- подгруппа;
- работа.

В режиме "Дерево" пользователь должен видеть и раскрывать иерархию.

В режиме "Колонки" пользователь должен видеть выбранный уровень в виде колонок и карточку выбранного узла. Если выбран верхний уровень разделов, внутри колонки не должно отображаться лишнее вложенное дерево, которое визуально дублирует структуру.

#### Справочник материалов

Справочник материалов должен позволять:

- хранить наименование;
- единицу измерения;
- категорию;
- синонимы;
- источник;
- статус;
- признак дубля;
- историю изменений.

#### Справочник единиц измерения

Справочник единиц измерения должен позволять:

- хранить краткое обозначение;
- полное название;
- тип;
- статус;
- связь с работами и материалами.

## 7. Логика ЦА

### 7.1 Общая роль ЦА

Цифровой ассистент должен быть помощником, который работает во всех ключевых сценариях. Он должен не только показывать текстовые подсказки, но и помогать пользователю выполнять конкретные действия.

ЦА должен:

- анализировать описание дефекта;
- предлагать работы;
- подбирать материалы;
- находить дубли;
- объяснять выбор;
- помогать исправлять ошибки;
- пересчитывать готовность документа;
- помогать сметчику с расценками;
- задавать уточняющие вопросы;
- формировать next best action.

### 7.2 Сценарий: у дефекта нет работ

1. Система обнаруживает дефект без связанных работ.
2. В блоке готовности появляется ошибка.
3. Пользователь нажимает "Решить".
4. ЦА показывает возможные работы.
5. Пользователь выбирает подходящую работу.
6. Работа добавляется к дефекту.
7. Ошибка снимается или меняется на "Нужно уточнение".
8. Готовность документа пересчитывается.

### 7.3 Сценарий: работа требует уточнения

1. ЦА определяет, что работа выбрана с низкой уверенностью.
2. Система показывает статус "Нужно уточнение".
3. ЦА задает вопрос пользователю.
4. Пользователь выбирает вариант или вводит ответ.
5. Система обновляет характеристику работы.
6. Статус меняется на "Готов" или остается в уточнении.

### 7.4 Сценарий: найден дубль материала

1. ЦА находит похожий материал в справочнике.
2. Пользователь открывает карточку дубля.
3. Система показывает исходную и похожую запись.
4. Пользователь выбирает действие:
   - использовать существующий материал;
   - объединить записи;
   - оставить отдельно.
5. Решение фиксируется.
6. Предупреждение снимается или остается с выбранным статусом.

### 7.5 Сценарий: пользователь нажал "Решить"

Кнопка "Решить" должна передавать контекст проблемы в ЦА. Пользователь не должен заново объяснять, о какой ошибке идет речь. ЦА должен сразу предложить релевантные варианты действия.

### 7.6 Сценарий: пользователь нажал "Принять подбор"

После нажатия:

- предложенные работы или материалы подтверждаются;
- статус позиции обновляется;
- блок готовности пересчитывается;
- пользователь получает понятное уведомление о результате.

### 7.7 Сценарий: пользователь нажал "Проверить заново"

После нажатия:

- система повторно проверяет документ;
- обновляет checklist;
- пересчитывает готовность;
- показывает новые ошибки или подтверждает, что документ готов.

## 8. Требования к интерфейсу

### 8.1 Общий стиль

Интерфейс должен выглядеть как современная clean enterprise SaaS-система:

- светлая тема;
- спокойный фон;
- белые карточки;
- аккуратные границы;
- мягкие тени;
- единый синий цвет для основных действий;
- зеленый цвет для успешных статусов;
- желтый/оранжевый для предупреждений;
- красный для ошибок;
- нейтральный серый для второстепенных элементов.

### 8.2 Навигация

Требования:

- навигация должна быть единой и понятной;
- не должно быть второго sidebar внутри страницы, если он дублирует основной;
- активный раздел должен быть визуально выделен;
- переходы не должны вести на пустые или сломанные страницы;
- для каждой роли должны отображаться только релевантные разделы.

### 8.3 Компоненты

Требования:

- все иконки должны быть в одном стиле;
- кнопки должны быть визуально кликабельными;
- tabs должны иметь активное состояние;
- stepper должен показывать текущий этап;
- таблицы должны быть читаемыми;
- карточки не должны быть перегружены;
- статусы должны быть различимы;
- длинный текст должен корректно переноситься;
- интерфейс не должен ломаться на масштабе браузера 100%.

### 8.4 Правая панель ЦА

Правая панель ЦА должна:

- занимать доступную высоту;
- показывать контекст текущей страницы;
- содержать сообщения;
- содержать быстрые действия;
- иметь input, закрепленный снизу;
- не перекрывать основной контент.

### 8.5 Пустые области

В системе не должно быть больших пустых областей без смысла. Если данных нет, нужно показывать:

- empty state;
- объяснение, почему список пуст;
- кнопку следующего действия;
- подсказку ЦА, если она уместна.

## 9. Валидация и ошибки

### 9.1 Проверки ДВ

Система не должна позволять отправить ДВ, если:

- не заполнен объект;
- не заполнена локация, если она обязательна;
- нет работ;
- есть blocking errors;
- отсутствует заявитель;
- отсутствует основание;
- не заполнена обязательная дата;
- есть критичные дубли материалов без решения;
- есть работа без единицы измерения;
- есть работа без объема, если объем обязателен.

### 9.2 Проверки ЕСЭД

- Возврат на доработку требует комментарий.
- Согласование невозможно без выбранного документа.
- После согласования статус должен измениться.
- После возврата заявитель должен видеть причину.

### 9.3 Проверки СМАКС

- Назначение требует выбора сметчика.
- Нельзя назначить закрытую заявку.
- Возврат заявителю требует причину.
- Отложенная заявка должна иметь понятный статус.

### 9.4 Проверки сметчика

- Закрытие сметы требует проверки всех позиций.
- Нельзя закрыть смету с необработанными ошибками.
- Нельзя принять позицию без расценки.
- Возврат на уточнение требует комментарий.

### 9.5 Отображение ошибок

Ошибки должны показываться через:

- toast;
- inline message;
- подсветку поля;
- карточку предупреждения;
- блок готовности;
- сообщение ЦА.

Текст ошибки должен объяснять не только факт ошибки, но и что нужно сделать дальше.

## 10. Требования к интерактивности

### 10.1 Общие требования

Все кнопки должны иметь действие. Нельзя оставлять декоративные кнопки, которые визуально выглядят рабочими, но ничего не делают.

Если промышленный backend еще не подключен, действие должно работать на демонстрационном состоянии, чтобы пользователь видел результат сценария.

После каждого действия пользователь должен видеть:

- изменение статуса;
- изменение данных;
- toast или inline-сообщение;
- обновление счетчиков, если они есть;
- переход на следующий экран, если сценарий этого требует.

### 10.2 Таблица действий

| Действие | Что меняется | Какой статус обновляется | Какой результат видит пользователь |
| --- | --- | --- | --- |
| Создать через ЦА | Создается черновик ДВ | Черновик | Открывается предпросмотр с подсказками. |
| Проверить заново | Пересчитывается готовность | Внутренние статусы проверки | Обновляется checklist и процент готовности. |
| Решить ошибку | Проблема передается в ЦА | Ошибка / Нужно уточнение / Готов | Появляются варианты решения. |
| Принять подбор | Подтверждаются работы или материалы | AI-подбор -> Готов | Позиция становится подтвержденной. |
| Отправить на согласование | ДВ уходит в ЕСЭД | Черновик -> На согласовании | Пользователь видит уведомление об отправке. |
| Согласовать в ЕСЭД | ДВ проходит согласование | На согласовании -> Согласовано | Запись передается в СМАКС. |
| Вернуть на доработку | Документ возвращается заявителю | На согласовании -> На доработке | Заявитель видит комментарий. |
| Назначить сметчика | Заявка получает исполнителя | Утверждена -> На осмечивании | Сметчик видит входящую задачу. |
| Подобрать расценку | Позиция получает расценку | Нужно уточнение -> Готов | Позиция считается обработанной. |
| Закрыть смету | Завершается работа сметчика | На осмечивании -> Смета готова | Смета передается дальше или закрывается. |

## 11. Ограничения MVP

### 11.1 Входит в MVP

Первая версия должна включать:

- создание ДВ через ЦА;
- ручное создание ДВ;
- предпросмотр документа;
- блок готовности;
- обработку ошибок и предупреждений;
- обработку дублей материалов;
- очередь ЕСЭД;
- согласование и возврат на доработку;
- очередь СМАКС;
- назначение сметчика;
- рабочее место сметчика;
- входящие сметы;
- черновик сметы;
- подбор расценок;
- базовую страницу старшего сметчика;
- справочники объектов, материалов, работ и единиц измерения;
- демонстрационные данные для проверки сценариев.

### 11.2 Не входит в MVP

В первую версию не входит:

- реальная интеграция с корпоративным ЕСЭД;
- реальная интеграция с промышленным СМАКС;
- production AI backend;
- полноценный расчет смет промышленного уровня;
- корпоративная авторизация SSO;
- полноценное файловое хранилище;
- сложная ролевая модель с детальными правами на каждое поле;
- юридически значимая электронная подпись;
- интеграция с внешними бухгалтерскими или ERP-системами.

## 12. Нефункциональные требования

### 12.1 Доступность и среда использования

Система должна быть доступна пользователям через веб-браузер. Основной сценарий использования рассчитан на desktop-экраны и рабочие ноутбуки сотрудников.

Минимальные требования:

- корректная работа в современных браузерах;
- стабильное отображение интерфейса на desktop-разрешениях;
- отсутствие критичных визуальных поломок при масштабе браузера 100%;
- возможность открыть основные страницы без специальных локальных инструментов со стороны пользователя.

### 12.2 Производительность

Система должна обеспечивать быстрый отклик интерфейса для основных действий.

Требования:

- основные пользовательские действия в демонстрационном режиме должны давать видимый результат в течение 1 секунды;
- переходы между ключевыми страницами не должны создавать ощущение зависания;
- длительные операции должны сопровождаться индикатором загрузки;
- пользователь должен понимать, что действие принято системой.

### 12.3 Надежность и сохранность действий

Система должна сохранять важные действия пользователей в истории.

В истории должны фиксироваться:

- создание ДВ;
- изменение статуса;
- отправка на согласование;
- согласование;
- возврат на доработку;
- назначение сметчика;
- принятие или замена расценки;
- закрытие сметы;
- комментарии и ключевые решения.

### 12.4 Права доступа

Права доступа должны зависеть от роли пользователя.

Общие правила:

- заявитель редактирует свои ДВ до отправки или после возврата на доработку;
- утверждающий ЕСЭД принимает решение только на своем этапе;
- координатор СМАКС распределяет только согласованные документы;
- сметчик работает только с назначенными ему сметами;
- старший сметчик проверяет готовые сметы;
- пользователь не должен видеть или выполнять действия, которые не относятся к его роли.

### 12.5 Безопасность

Система не должна хранить секреты, пароли, токены и ключи в пользовательском интерфейсе. Доступ к данным и действиям должен проверяться на стороне серверной логики при промышленной реализации.

## 13. Технические рекомендации

Этот раздел не является описанием текущей реализации. Он фиксирует рекомендации для дальнейшей разработки.

Рекомендуется:

- реализовать frontend на текущей прототипной базе или перенести интерфейс на современный frontend-framework по решению команды;
- backend строить как REST API;
- описать API через Swagger/OpenAPI;
- хранить права доступа на уровне ролей;
- фиксировать все важные действия в истории;
- не хранить секреты, пароли, токены и ключи на frontend;
- предусмотреть безопасную демонстрационную среду для сценариев без промышленной интеграции;
- отделить демонстрационные данные от production-данных;
- предусмотреть возможность подключения реальных ЕСЭД, СМАКС, справочников и AI-сервисов на следующих этапах.

## 14. Acceptance Criteria

### 14.1 Функциональные критерии

1. Все роли открывают свои страницы.
2. Навигация работает для каждой роли.
3. Создание ДВ через ЦА работает.
4. Ручное создание ДВ работает.
5. После шага "Работы" открывается предпросмотр документа.
6. Предпросмотр ДВ отображается как live document workspace.
7. ЦА помогает решать ошибки.
8. Пользователь может обработать дубль материала.
9. ДВ можно отправить на согласование.
10. ЕСЭД может согласовать ДВ.
11. ЕСЭД может вернуть ДВ на доработку.
12. СМАКС может назначить сметчика.
13. СМАКС может отложить заявку.
14. СМАКС может вернуть заявку заявителю.
15. Сметчик может открыть входящую смету.
16. Сметчик может открыть черновик.
17. Сметчик может подобрать расценку.
18. Сметчик может заменить расценку.
19. Сметчик может закрыть смету после проверки всех позиций.
20. Старший сметчик может проверить готовую смету.

### 14.2 UI/UX критерии

1. Интерфейс не ломается на 100% масштабе браузера.
2. Нет больших пустых областей.
3. Нет дублирующих sidebar внутри страниц.
4. Правая панель ЦА занимает доступную высоту.
5. Input чата закреплен снизу.
6. Все кнопки выглядят и работают как кликабельные элементы.
7. Таблицы читаемые.
8. Статусы визуально различимы.
9. Tabs и stepper кликабельны.
10. Empty states объясняют пользователю, что делать дальше.

### 14.3 Критерии интерактивности и качества

1. Все кнопки имеют обработчики.
2. После каждого действия пользователь видит результат.
3. Статусы обновляются визуально.
4. Ошибки показываются через toast или inline-сообщение.
5. Нет пустых страниц.
6. Нет console errors.
7. Возврат на доработку требует комментарий.
8. Назначение требует выбора сметчика.
9. Закрытие сметы требует обработки всех позиций.
10. Дубли материалов требуют решения или явного подтверждения.
